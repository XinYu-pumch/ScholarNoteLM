## 2. 已在代码中确认的缺陷

### 2.1 状态查询触发写操作，日志无限增长（高）

**现象**：本项目 `logs/` 在 53 分钟内生成了 297 个 `corpus-files-*.json`，大约每 10 秒一个，内容都是 `"deleted": ["markdown/redundant"]`。其他项目累计情况：gut 50,929 个、HLH 38,549 个、PrimaryMN 21,693 个、BD2026 14,354 个、HUSandgene 10,758 个，**合计约 13.6 万个**。

**原因**：`markdown.status` 每次被界面轮询时，都会调用 `corpus_files.reconcile_locked`（`services/downloader/markdown_service.py:67`）。对账时执行以下步骤：

1. `folder()` 在读取路径时会顺手 `mkdir`（`corpus_files.py:40`），所以第 81 行遍历 `markdown/redundant/raw` 时，自动建出了空的子目录。
2. 第 118 行据此判定 `markdown/redundant` "非空"，`rmtree` 后记为已删除。
3. 第 159 行再写一条日志。

下一次轮询又会重复上面这三步。项目创建后的第一次 `workspace` 调用已经返回 `deletedDerived: 1`，说明与本次操作无关，平时打开 app 也会发生。

**已修复（2026-10-04）**：
- `corpus_files.py` 新增不建目录的 `existing()`。已停用的 `markdown/redundant`、`markdown/redundant/raw`、`markdown/redundant/assets`、`abstracts/redundant` 只读取、不再创建。
- 清理旧目录时，只有其中确实有文件才计入 `deleted` 并写日志；旧版本遗留的空目录会被安静地删除，不写日志。
- 新增回归测试 `test_idle_reconcile_writes_nothing` 和 `test_empty_legacy_folders_removed_without_log`。原有的"旧版 redundant 中真实文件仍被清理"测试继续通过。
- 用真实 RPC 验证：本项目连续 3 次 `markdown.status`，日志数量不变。
- 历史日志：136,578 个只记录了 `deleted == ["markdown/redundant"]`、没有任何移动、恢复、归档或报错的条目，已打包到 `backups/corpus-files-noise-20261004.tar.gz`（核对条目数一致后才删除），每个项目保留最早的一条；其余 14 条记录真实变动的日志未动。
- 仍可后续考虑：状态查询每次仍会解析 `current.xml` 并遍历目录。现在已经没有写入，但开销还在，可以改为在任务开始和结束时对账。

### 2.2 Sci-Hub 镜像返回 403 后不降级（中）

**现象**：`sci-hub.box` 在本批次里连续 23 次返回 `forbidden`，每次仍被正常调度，全部失败。

**原因**：`scihub_retry.py:143-158` 只对 `tls_certificate`（停用）、`rate_limited`（冷却）、`timeout/network_error/temporary_server_error`（3 篇后冷却）做了处理；`forbidden` 落入 `else` 分支，只清空 `failedArticles`，既不冷却也不停用。

**建议**：同一批次内同一入口连续 N 次（例如 3 次）`forbidden` 后，本批次停用或进入长冷却；成功一次即恢复。

### 2.3 一键更新的下载计数显示为 0（低）

`library_service.py:131` 汇总阶段结果时读取 `result['completed']`，但下载结果把成功数放在 `success` 字段，所以任务记录显示"下载：完成 0 / 失败 18"，而实际成功了 96 篇（另有 3 篇来自 Zotero）。修正字段映射即可，也可以让下载结果同时输出 `completed`。

### 2.4 "部分完成"语义容易误读（低）

18 篇无 PDF 的文献已按设计改用摘要，转换和索引全部完成，一键更新仍显示 `partial`。建议区分两种情况：

- "完成（18 篇使用摘要）"：流程正常结束。
- "部分完成"：确有阶段失败。

## 3. 内容质量问题

### 3.1 综述跨章节自相矛盾（高）

- **3.4.2 节**"抗PLA2R1 IgG在转基因小鼠中诱导膜性肾病样损伤"写道："就本项目当前检索到的证据而言，**尚未见**抗PLA2R1 IgG在转基因小鼠中诱导膜性肾病样损伤的直接实验数据"。
- **8.3.2 节**"人PLA2R1转基因小鼠模型模拟膜性肾病病理"依据 **PMID 37598854**（chPLA2R1 小鼠主动免疫后出现完整 MN 表型）做了详细描述。

**根因**：大纲由 deepseek-v4-pro 根据全部摘要生成，这个标题本身就来自 37598854 的摘要。但写作时每个终末标题独立召回，3.4.2 的 7 个块里没有这篇文献。也就是说，大纲知道的证据，写作阶段未必能拿到。README 第 7 节记录的 5.5.2/6.3.1 不一致属于同类问题，这次再次出现。

**建议**：
1. 大纲生成时让模型为每个终末标题输出"锚点 PMID"，写作材料池强制纳入锚点文献的摘要或全文块。
2. 全文生成后，对同一 PMID 在不同单元中的表述做一致性检查，至少把"尚未见/缺乏"类否定表述与其他单元引用同一主题的情况标出来。

### 3.2 中文标题检索英文文献，召回偏弱（中，需要产品决策）

- 75 个终末标题的最高相似度中位数只有 0.615，最低的几个在 0.52–0.55（"髓系细胞趋化和吞噬相关改变"、"细胞间通讯网络放大肾小球损伤"等）。
- "体外足细胞模型和器官芯片系统"一节召回的是电镜图注、治疗流程图和预后算法，模型据此写道"没有任何一条来自体外足细胞培养或器官芯片系统本身的研究"。但项目里其实有 glomerulus-on-a-chip 相关文献（34593809、38227377）。
- 问答的检索词同样是长中文问句。第二问专门检索了"PLA2R 转基因或主动免疫模型"，仍然没有召回 37598854，回答因此只提到"缺乏直接被动转移模型"，遗漏了已有的主动免疫转基因模型。

**小实验**（`vector.search`，4 条查询，样本很小，只能作为初步证据）：

| 查询 | 目标文献排名（前 10） |
| --- | --- |
| 中文：抗PLA2R1 IgG在转基因小鼠中诱导… | 37598854 未进前 10 |
| 英文：Anti-PLA2R1 IgG induces … transgenic mice | 37598854 **第 5** |
| 中文：体外足细胞模型和器官芯片系统 | 38227377 第 10，34593809 未进 |
| 英文：In vitro podocyte models and glomerulus-on-a-chip … | 34593809 **第 3** |

**建议**：README 当前决定第 7 条规定"Query 使用终末标题原文；中文不翻译英文"。建议把"中文标题 + 英文翻译双查询、合并去重"做成**可选项**，先在本项目上用 75 个标题做对照评估，再决定是否默认开启。问答规划器也可以要求每个 query 额外给出一条英文关键词式检索。

### 3.3 低价值文本块占用召回名额（中）

- 全部 9243 块中，`blockType` 只有 paragraph / heading / table / caption 四类，基金、版权、作者贡献、利益冲突等内容都被标成 paragraph。按正则粗略统计约有 **356** 块。
- 综述实际召回的 525 块里：
  - **37 块（7%）不足 120 字符**，例如文章标题、"Supplementary Methods"、"Two validation cohorts were used."、关键词行。
  - **6 块**是基金或补充材料，例如 32933213 的 Funding、37257088 的资助说明、25766759 的 Table S2 图注。
- 每节只有 7 个名额，这些块会直接挤掉真正的证据。

**建议**：
- 按 `sectionPath` 和首行模式把 Funding / Acknowledgments / Author Contributions / Copyright / Disclosures / Supplementary 等归为 `backmatter` 并排除出召回，原文块保持不变，与现有段落分块决定不冲突。
- 目前只对 heading 适用的"少于 100 字符排除"规则，可以扩展到纯标题样式的短 paragraph。

### 3.4 "总结上述对话"几乎是照抄（中）

第三问被正确识别为改写意图（不重新检索，沿用原引用），但产出 11,814 字，是前两问合计 13,241 字的 89%；136 个长句里有 **75 句（55%）与前两问逐字相同**。引文确实保留了，但起不到总结的作用。

**建议**：改写 / 总结意图的提示词加入目标篇幅（例如原文的 20–30%），要求按要点重组，禁止整段复制；生成后统计逐字重复率，超过阈值时提示或自动重写一次。

## 5. 流程编排

1. **大纲生成被一键更新锁住**：在下载期间启动大纲时报"一键更新或清理正在运行"（`library_service.py:27`）。大纲只依赖当前 XML 的摘要，与下载、转换、索引互不影响，可以考虑放行。本次如果并行，可省下约 2 分钟。
2. **批量操作只在前端编排**："加入检索式"（解析聊天代码块）和"执行全部"（串行 + 2 秒间隔）都写在 `SearchWorkbench.tsx` / `search-proposals.ts` 里，后端没有对应的批量任务。离开页面会中断，脚本化或自动化时也必须复刻前端逻辑。建议把"执行全部检索式"做成后端任务，与下载、转换一样可以在任务中心查看。
3. **转换等下载全部结束才开始**：Marker 是全流程最大的耗时（12 分 22 秒，约 7.5 秒/篇），而下载持续了约 5 分钟。如果每篇 PDF 发布后立即进入转换队列，墙钟时间最多可缩短约 5 分钟。
